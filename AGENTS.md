# Инструкции и карта проекта для агентов

Этот файл — стартовая точка для будущих агентов, работающих с репозиторием.
Перед изменениями прочитай его, затем документацию и исходники нужного модуля.
Описание отражает реализованное поведение; при расхождении с документацией
сверяйся с текущим кодом и исправляй устаревшее описание.

## Назначение и возможности

«Фортуна» — умный универсальный помощник на компьютере пользователя.
Система сохраняет историю диалогов, использует доступный контекст пользователя
и помогает с задачами, документами и выбранной папкой workspace.
Основной интерфейс — чат. Приложение использует React + TypeScript
и Vite, FastAPI, desktop-оболочку Tauri на Rust, SQLite и Chroma.
Генерация и embeddings работают через отдельные локальные llama-server с
GGUF-моделями; обязательной зависимости от Ollama нет.

Пользовательское название в интерфейсе, экспорте чатов, окне desktop,
настройках installer и общих инструкциях ассистента — «Фортуна».
Идентификатор `local.kontur.rag`, ключи localStorage, переменные `KONTUR_*`
и имя backend сохранены для совместимости существующих данных и запуска.

Реализованы:

- Загрузка PDF, DOCX, HTML и TXT, импорт папок Google Drive, поиск,
  переиндексация и удаление документов из общей библиотеки.
  Повторный импорт по Drive ID обновляет документ; источник и решение о замене
  индекса сохраняются одной SQLite-транзакцией. Обновление источника исключает
  устаревшие ответы из скрытого контекста модели.
- Обычный ответ workspace и библиотеки использует контекстную сверку
  (`api/answer_review.py`, `ANSWER_REVIEW_MODE=contextual` по умолчанию).
  Связный черновик сохраняет абзацы и полезные сведения. Контекстная оценка
  проверяет все выбранные источники; при переполнении делится ответ, документы
  не исключаются. Положительные утверждения дополнительно проходят независимый
  аудит участника, действия с объектом и модальности. Правила не содержат
  словаря предметной области. Можно исправить несколько предложений; после
  замечаний независимого аудита допускается один этап точечных исправлений.
  Все новые формулировки сверяются заново. Неизменённые предложения не переписываются.
  При обрыве обычной генерации workspace сохраняет законченные предложения,
  показывает причину ограничения и хранит полный исходный черновик в журнале.
  Интерпретация, отсутствие сведений, противоречие и технический сбой различаются.
  При отказе сверки сохраняются ответ и `UNAVAILABLE`, без ложного подтверждения.
  Замечания не запускают отбор одних фактов, повторный синтез обзора или замену
  объяснения единственной цитатой. Панель показывает модельную оценку,
  замечания и изменения без процента «уверенности».
  Строгая проверка доступна в `/agent/verify` и через
  `ANSWER_REVIEW_MODE=strict`. Следующее описание прежней проверки утверждений,
  предварительной подготовки обзоров и восстановления относится к строгому режиму.
  См. [docs/contextual-answer-review.md](docs/contextual-answer-review.md).
- Обычный диалог, RAG, GraphRAG, строгая проверка ответов по источникам
  и внутренняя редактура draft → edit → enhance → merge. Ручная пошаговая
  мастерская и выбор режима редактуры убраны из UI: пользователь получает готовый
  результат. Обычный текстовый запрос интерфейса включает `use_multi_agent=true`
  для библиотеки и workspace; FAST выполняет одну редактуру, остальные профили
  могут улучшить и собрать текст при достаточном остатке общего бюджета.
  Итог проверяется после редактуры по тем же источникам, версии сохраняются в журнале.
  Совместимые `/agent/*` остаются для прежних клиентов; workspace передаётся явно.
  Отсутствие запрошенного факта обозначается как недостаток информации. Запасной
  ответ использует только проверенные утверждения; инструкции, обращённые к
  ассистенту внутри источника, исключаются из фактических доказательств.
  При выбранном workspace переход к импортированной библиотеке требует явного
  запроса пользователя, включая многошаговые планы.
- Assistant Core: сессии, задачи, действия, события, отмена генерации,
  планирование шагов и выполнение зарегистрированных навыков knowledge и workspace.
  Прямые запросы содержимого и известные имена файлов обрабатываются до LLM-планировщика
  и переписывания истории. Операции плана и маршрутизатора проверяются по исходной
  реплике пользователя; кеш маршрутизации всего запроса не переносится на другую подзадачу.
- Выбор локального workspace, просмотр и чтение файлов, поиск последней версии,
  сравнение версий, системные даты и открытие файла системным приложением.
  Есть индекс метаданных, векторная индексация и граф для workspace.
  Изменение, удаление и переименование исходных файлов workspace не реализованы.
- История чатов в SQLite, разрешение ссылок на файлы и контекст предыдущих сообщений.
  Ссылки «в этом файле» сохраняют активный источник без LLM-переписывания;
  явно названный новый файл имеет приоритет. Для «что внутри …» проверяются
  реальные имена файлов/папок, обычный предмет вопроса не становится именем файла.
- Проверка отсутствующих сведений нормализует явные сообщения о недостатке
  информации даже при неверном `basis` модели. При смешанном ответе сохраняется
  подтверждённая часть; отсутствие нужного факта не заменяется биографией.
  `VerificationClaim.relevant_to_question` отделяет недостаток сведений по
  текущему вопросу от посторонних тем; все утверждения сохраняются в проверке.
  Схема генерируемой проверки требует все поля утверждений, несмотря на defaults
  для чтения старых данных: иначе модель может опустить цитаты и скрыть верный ответ.
  Длинные ответы проверяются по частям на границах предложений/строк; при обрыве
  JSON часть разбивается повторно с ограничением числа попыток. Проверяются все
  части, включая последние. Провайдер сохраняет `finish_reason` и отличает
  исчерпание токенов от ошибки JSON; незавершённая проверка не считается успешной.
  Инструкции проверки передаются отдельно от источников и текста ответа.
  Ошибочная метка `UNANSWERED` у неподтверждённого положительного факта не
  превращает его в сообщение, что в документах отсутствует ответ на весь вопрос.
  В обзорном вопросе подтверждённые фрагменты сохраняются и при отсутствии
  некоторых деталей, даже если модель ошибочно отметила этот пробел как относящийся
  к вопросу. Запрос одного отсутствующего факта по-прежнему не заменяется биографией.
  После проверки дословных цитат каждый положительный факт дополнительно
  проверяется на совпадение субъекта, действия и модальности. Ошибка/обрыв этой
  оценки не считается подтверждением. Прямое утверждение «в тексте сказано: …»
  проверяется по точной цитате в указанном источнике без дополнительной трактовки.
  Исправление ответа использует исходные источники и компактные подтверждённые утверждения,
  затем весь новый ответ проверяется повторно. Полный черновик и отчёт проверки
  не дублируются в контексте исправления. Частично подтверждённый ответ сохраняет
  прямое объяснение, если все его факты подтверждены, а остальные утверждения
  обозначают недостаток сведений. Короткие вопросы «кто такой» и «что знаешь о»
  получают обычный бюджет; явная просьба подробного анализа имеет приоритет.
  Неудачное исправление без подтверждённых относящихся к вопросу фактов не
  стирает предыдущую проверенную часть. Запасной ответ может использовать полные
  подтверждённые утверждения с действительными цитатами и ссылками; обрывки,
  посторонние факты и неподтверждённые утверждения не включаются.
  «Что за/что такое» также считаются короткими обзорными вопросами. Для короткого
  обзора генератор получает тематические абзацы с контекстом; полный найденный текст
  сохраняется для проверки. Обычный ответ не ограничивается четырьмя предложениями
  или одной ролью: объём определяется вопросом и сведениями в источниках.
  «Кто такой» использует общую подготовку содержательного обзора по источникам
  у структурированного провайдера; отдельного маршрута с одним самоназванием нет.
  Короткое описание с самоназванием в конце сохраняет контекст говорящего;
  рамки «В текстах» и явные сообщения о самописании учитываются в аудите.
  Проверенные Markdown-цитаты сохраняются при слиянии с восстановленным ответом.
  Локальное «Мирон заявляет, что он…» не теряется из-за запрета всех местоимений;
  ссылки на удалённые предложения не переносятся.
  Неизменённый проверенный текст синтезатора не проверяется повторно при восстановлении.
  После успешного восстановления запасной этап с самоназванием не запускается.
  Один проверенный факт не закрывает другие сведения того же файла.
  См. [docs/answer-informativeness.md](docs/answer-informativeness.md).
  Независимый вопрос не получает старые ответы чата;
  для продолжения используются признак `depends_on_history` и самостоятельный вопрос.
  Смысловая проверка отдельно оценивает относимость факта к вопросу, различает
  намерение/совет/условие/самоописание и факт. Общее определение из соседнего абзаца
  не заменяет описание названной организации. Самовнушение в примере не является
  биографией персонажа; безличный совет не приписывается ему по соседству с именем.
  После неудачного ответа может быть восстановлено прямое самоназвание из источника
  вне условного примера; противоречивые самоназвания не выбираются произвольно.
  Этот запасной ответ проходит обычную проверку, включая смысл и относимость.
  Журнал хранит `GENERATE_RESPONSE.draft`, `VERIFY_RESPONSE` и `FINALIZE_RESPONSE`.
  Панель оценивает именно `checked_answer`: отсеянные факты остаются в черновике и
  журнале, а показатели пересчитываются по показанным неизменным проверенным фразам.
  Новый пересказ не наследует старое подтверждение. Контекст доказательства сохраняет
  цитату и явное имя говорящего, в том числе в конце файла.
  Короткое объяснение темы подготавливается по дословным тематическим фрагментам
  с контекстом примера, адресата и самоназвания (`overview_synthesis.py`).
  Структурированный провайдер сначала независимо проверяет атомарные сведения
  (`overview_facts.py`), затем пишет только по ним. Новый пересказ отдельно
  проверяется по допущенному сведению; соседний текст источника писателю не доступен.
  Сохраняются атрибуция документа, противоречия источников и неиспользованные
  проверенные сведения. После одной неудачной попытки пересказа используются
  исходные проверенные предложения; дословные цитаты остаются `LIMITED`.
  Подготовка и отказы сохраняются в `GENERATE_RESPONSE.data.fact_preparation`.
  После успешного смыслового аудита явная привязка пересказа к конкретному
  документу сохраняет документальную область даже при ошибочной метке `FACT`;
  это не подтверждает содержание и не исправляет отказ по относимости.
  Причина сохраняется как `scope_adjustment=explicit_document_frame`.
  Неизменённый проверенный итог не проверяется повторно. Границы описаны в
  [docs/fact-first-overviews.md](docs/fact-first-overviews.md). Для этой
  цепочки рассуждение следует профилю, с отдельным бюджетом для ответа. Нативная
  подготовка BALANCED использует короткий бюджет 128 токенов; последующий аудит
  BALANCED и весь FAST идут без рассуждения.
  Локальный провайдер выбирает доказательства по ID исходных фрагментов без
  переписывания длинных цитат. Смысловой аудит остаётся отдельным. Подготовка
  допускает до восьми предложений на обзор, включая сведения одного источника; провайдеры
  без поддержки ID сохраняют прежний контракт цитат и границы 3/6.
  FAST и BALANCED возвращают эти неизменённые проверенные предложения абзацами,
  сохраняя самописание и намерения без повторения имени файла в каждой фразе,
  если предложение уже содержит явную атрибуцию. REASONING может пересказывать
  сведения с независимой проверкой нового текста.
  «Если ты …, то я …» с сохранённым условием и явно названным говорящим
  не теряется как действие адресата; анонимный голос не связывается с именем.
  Вся модельная цепочка имеет общий бюджет FAST/BALANCED/REASONING 120/180/240 секунд;
  отдельный вызов — 90/90/120. Продолжающийся поток токенов не продлевает бюджет.
  Истечение времени закрывает поток, не считается отменой пользователя или
  подтверждением неполной проверки; проверенные сведения сохраняются.
  Запись субъекта «Говорящий (Имя Фамилия)» сохраняет имя для проверки;
  «сообщает адресату, что …» распознаётся как отчёт о словах источника.
  При неудачном пересказе могут сохраняться исходные цитаты явно названного
  голоса, как сообщения о тексте с отдельным доказательством происхождения,
  не как подтверждение отвергнутого пересказа. Прямое непротиворечивое
  самоназвание может восстановить вводную фразу перед остальным объяснением.
  См. [docs/response-latency.md](docs/response-latency.md).
  Каждое предложение готовится отдельно по одному фрагменту, чтобы не смешивать
  атрибуцию разных документов. Дословно скопированный текст источника оформляется
  цитатой; обращение автора к адресату не становится обращением ассистента к пользователю.
  Проверка оценивает неизменённые предложения; изменение или пропуск предложения
  делает оценку незавершённой. Из смешанного ответа можно сохранить целые проверенные
  предложения, если они дают содержательное объяснение без потерянных местоименных
  ссылок. Новое описание проверяется заново. `answer_scope` отделяет объяснение
  (`EXPLANATORY`) от отдельных сведений (`LIMITED`): подтверждение цитат не означает
  полноту ответа. «Как создавался ответ» показывает черновик до проверки, не reasoning.
  Относимость прямого описания точно названного предмета может быть восстановлена
  правилом после успешной проверки факта; это правило не подтверждает сам факт.
  Смысловая оценка извлекает субъект, действие с объектом и модальность до вердикта.
  Подсчёт токенов повторно обращается к серверу после временного сбоя загрузки:
  оценка по байтам UTF-8 не кешируется и не отключает последующие попытки tokenizer.
  Кешируются только результаты реального tokenizer. Проверяй этот сценарий до
  загрузки модели и после её готовности, включая повтор того же самого prompt.
  Невозможность вместить проверку в контекст — `UNAVAILABLE`, а не отсутствие
  сведений в документах. При техническом отказе без оценённых утверждений workspace
  сохраняет причину в итоговом ответе и журнале, не запускает повторный синтез
  и не предлагает уточнить уже корректный вопрос.
  В обзорном ответе постороннее, но подтверждённое предложение также запускает
  отбор уже проверенных предложений; общий статус `SUPPORTED` не означает,
  что все предложения отвечают на вопрос. Сохрани подходящее объяснение до
  повторной генерации.
  Направление отношений проверяется общим смысловым аудитом вместе с действием
  и его объектом; специальных правил для отдельного глагола нет.
  Явное сообщение о словах говорящего в тексте совместимо с `SELF_DESCRIPTION`,
  даже при ошибочной оценке модальности моделью; субъект, действие, цитата и
  привязка говорящего всё равно проверяются. Правило не распространяется на
  примеры самовнушения и не превращает самоназвание в факт реального мира.
  `guard_rejection` и `guard_adjustment` сохраняют причину решения рядом с
  исходными полями модельной оценки в журнале.
  Буквальные сообщения о тексте сопоставляются с исходными источниками до
  модельного выбора цитаты; неподтверждённые трактовки проверяются отдельно.
  Защита адресата не применяется к субъектам-документам; причины отказов
  привязки говорящего/адресата и усиления модальности сохраняются в журнале.
  Восстановление обзора объединяет неизменённые подтверждённые относящиеся
  к вопросу предложения, не заменяя полезные факты одними упоминаниями.
  Пример с предшествующим контекстом можно объяснить как приём в заметке;
  пример без контекста остаётся дословной цитатой и не считается биографией.
  Узкие сообщения о структуре текста проверяются по дословной фразе требования
  с сохранённой модальностью и по явному перволичному примеру с названием.
  Эти правила подтверждают текстовый контекст, не реальность персонажа.
  Общее определение понятия не подтверждает определение названного частного
  предмета: явная лексическая подмена отклоняется даже при положительной оценке
  модели. Для `EXPLANATORY` нужны два содержательных проверенных предложения;
  цитаты и упоминания названия этот порог не заполняют. При обращении модели
  к пользователю от лица источника синтез сохраняет исходную фразу цитатой
  и продолжает другие фрагменты. Границы защиты описаны в
  [docs/user-query-evaluation.md](docs/user-query-evaluation.md).
  Дословное сообщение о самоназвании проверяется по тексту независимо от
  формулировки вопроса, исключая примеры и условия. При восстановлении строка
  `Источники:` не передаётся как факт для проверки. Отдельного быстрого маршрута
  для «Кто такой …?» нет; см. [docs/person-identity-response.md](docs/person-identity-response.md).
- Голосовой ввод и Live-диалог с потоковыми ответами и озвучкой;
  распознавание через Whisper, TTS через CosyVoice с системным fallback.
- Desktop-запуск backend как sidecar, статус моделей и сборка Windows installer.
- Выбор установленных Qwen 3.5 4B, 9B Q4/Q3 и Gemma 4 E4B в шапке чата
  отдельно от FAST/BALANCED/REASONING. GGUF хранятся на диске; активна одна chat-модель. Переключение перезапускает
  только принадлежащий приложению llama-server, не трогая embeddings. Выбор
  сохраняется в `DATA_DIR/chat-model-selection.json`; без сохранённого выбора
  используется исходная конфигурация (в текущем dev — 4B). Нельзя переключать
  модель во время задачи/генерации или останавливать чужой сервер.
  Для JSON при выключенном размышлении провайдер применяет нулевой бюджет
  reasoning и шаблон с доступными серверу разделителями. Обычный текст сохраняет
  выключенный шаблон: его принудительное включение может вывести анализ в ответ.
  Реальные замеры и ограничения качества описаны в
  [docs/local-model-alternatives.md](docs/local-model-alternatives.md).

- Оптимизация RAG: смысловой аудит до двух изолированных утверждений с
  возвратом к одиночным проверкам при отказе пакета; `EVIDENCE_AUDIT_BATCH_SIZE=1`
  отключает пакеты. FAST-обзор использует неизменённые проверенные предложения,
  автоматическая FAST-редактура — draft → edit. Снимки обхода workspace
  переиспользуются внутри запроса до одной секунды; неизменённые строки не
  перезаписываются. Провайдер переиспользует HTTP-клиенты и измеряет подготовку
  и полное время вызова. Смысловой граф документов дополняет обычный поиск
  без новых модельных вызовов. Извлечённые отношения остаются подсказками
  для поиска и не считаются подтверждёнными фактами. См. [docs/rag-performance.md](docs/rag-performance.md).
- Явный информационный вопрос без операций и последовательности шагов пропускает
  LLM-планировщик workflow, включая «к кому/с кем/для кого». В активной папке
  такой вопрос получает область workspace по правилу без модельного маршрутизатора;
  явная библиотека и распознанная беседа сохраняют свои маршруты. Короткий вопрос
  получает обычный бюджет без модельного выбора подробности; явный анализ имеет приоритет.
  Поиск и проверка ответа выполняются.
  Нативная проверка обычного черновика использует ID неизменённых предложений и
  нескольких дословных исходных цитат. Тип предложения задаётся обязательным
  `contains_positive_facts`: положительный факт вместе с пробелом не становится
  чистым `UNANSWERED`. Положительные факты по-прежнему проходят независимый
  смысловой аудит; отсутствующее предложение/неизвестный ID не принимаются.
  При истечении времени сохраняются завершённые оценки частей и отдельных фактов,
  ожидающие аудита остаются `UNAVAILABLE`. Итог может использовать только целые
  проверенные относящиеся к вопросу предложения и проверенное указание на пробел.
  Причина остановки показывается явно, без повторного восстановления после срока.
  Технический отказ исправления и `UNAVAILABLE` повторной проверки сохраняют
  оценки исходного ответа и причину отказа; новый пересказ не наследует их.
  См. [docs/partial-answer-checks.md](docs/partial-answer-checks.md).
  Прямые вопросы об имени и числовых параметрах получают краткий бюджет без LLM;
  явная просьба анализа и обзор имеют приоритет. Защита атрибуции узнаёт регулярные
  падежи ролей на «-тель» в самой цитате; это не связывает анонимное «я/ты» с именем.
  Менеджер llama-server переиспользует HTTP-клиент, проверяет readiness и alias
  при каждом обращении и закрывает транспорт при остановке; повторный запуск
  создаёт новый клиент.
- Извлечение новых графовых отношений сохраняет только связи с цитатой,
  найденной в указанном фрагменте; неизвестный/неверный chunk ID разрешается
  только по единственному совпадению цитаты, без назначения первого фрагмента.
  Это проверка происхождения, не смысловое подтверждение отношения. Уже
  сохранённые графы не переписываются без переиндексации.
- Граф автоматически помогает обычному чату и draft/edit. `graph_retrieval.py`
  строит кеш связей точных имён/идентификаторов по исходным фрагментам, без LLM.
  Для конкретного вопроса с явно найденным объектом ищет до двух переходов,
  сохраняет фрагменты пути и альтернативные прямые сведения. Только при полном
  лексическом покрытии вопроса и достаточном лимите источников пропускает новый
  embedding/MMR-вызов. Обзоры, сравнения, недостаточное покрытие, большой или
  устаревший индекс возвращаются к обычному hybrid. Это выбор источников,
  не подтверждение ответа; генерация и проверка остаются обычными.
  Запасное расширение добавляет до одного фрагмента с новым совпадением по вопросу;
  уже покрытый вопрос не получает сосед только по сходству. Workspace выбирает
  релевантный фрагмент-якорь вместо первого и помещает дополнение в остаток
  бюджета, не сокращая прямые выдержки. `GRAPH_RETRIEVAL_ENABLED=false`
  отключает новый поисковый слой; `graph_fast_path` и `graph_path` сохраняются
  в метаданных/журнале. Смысловая карта по embeddings остаётся отдельной
  визуализацией; точные упоминания поискового графа не выдают доказанные отношения.
  Для папки проверяются namespace, свежесть векторов и текущий файл; граф работает
  даже при неудачном LLM-извлечении отношений. Явные запросы файла/папки не расширяются.
  Карта в меню показывает близость документов по embeddings: круглые узлы,
  силовое размещение, поиск, подсветка соседей, перетаскивание и масштаб. Отдельные
  вопросы и цепочки убраны из UI; ответы используют обычный чат. Нажатие на линию
  открывает компактное пояснение с близостью и двумя исходными фрагментами.
  `/graph/map` разделяет workspace и библиотеку и показывает охват индекса.
  `/graph/link` возвращает пояснение только существующей линии в той же области,
  проверяет принадлежность и свежесть источников; изменённый источник — 409.
  Для длинного документа сравнивает выборку до 64 фрагментов и сообщает `sampled`.
  Пояснение не вызывает LLM и не назначает тип или причинность отношения.
  Старые API графа и `graph_selection` сохранены для совместимости истории.
  Порог `SEMANTIC_GRAPH_SIMILARITY=0.82`, выбор соседей `SEMANTIC_GRAPH_NEIGHBORS=3`.
  В окне Workspace кнопка «Индексировать папку» создаёт/обновляет embeddings
  рекурсивно без LLM-извлечения отношений; видны охват индекса и ошибки.
  Выбор workspace обновляет только метаданные. Для UI доступны
  `/workspaces/{id}/index-status` и `/workspaces/{id}/vector-sync?extract_relations=false`;
  API без параметра сохраняет прежнюю индексацию с извлечением отношений.
  Смысловая близость не подтверждает факты. См. [docs/graph-workbench.md](docs/graph-workbench.md).

- Локальный API проверяет Host, Origin и токен запуска до обработчиков. Desktop
  передаёт случайный токен через IPC, web/dev получает его через `/access-token`
  с обязательным заголовком `X-Fortuna-Client: web`. Все чувствительные маршруты
  требуют `X-Fortuna-Token`; `/api/health` остаётся доступным для readiness.
  Есть ограничения JSON и потокового тела загрузки до form-парсера; urlencoded
  на upload не принимается. Файлы credentials по именам и характерным признакам
  в первых 64 КиБ исключены из доступа workspace. Скрипты, программы, ярлыки
  и неизвестные форматы нельзя передавать системному opener.
- Ответ, журнал контекста и завершение задачи сохраняются backend одной SQLite-
  транзакцией. `request_id` предотвращает повторную генерацию уже завершённого
  сообщения; `assistant_responses` хранит результат. Список чатов — страницы по
  50 с поиском на сервере, сообщения загружаются отдельно. Версия чата защищает
  от устаревшей записи. SQL истории модели читает последние три пары сообщений.
  `/assistant/stream` передаёт ID задачи для отмены обычного ответа; промежуточные
  генерации не транслируются как итог. Старые `/assistant/input`, `/query` и Live
  сохранены.
- Извлечение ограничивает распакованный XML, объём текста, страницы PDF, пиксели
  и время OCR, число одновременных обработок; переполнение не обрезается молча.
  Ошибка полноты PDF не заменяется частичным text-layer fallback. Drive ограничен
  числом файлов, глубиной, байтами и временем; частичный импорт показывает пропуски.
  INFO-журнал не содержит превью страниц и распознанной речи. Desktop-миграция
  использует SQLite backup, staging и журнал повторного запуска, сохраняя исходники
  и существующие пользовательские данные. Границы, тесты и необходимость отзыва
  исторического ключа описаны в [docs/review-fixes-2026-10-15.md](docs/review-fixes-2026-10-15.md).

## Запуск и проверка изменений

Команды выполняются из корня репозитория в PowerShell. Используй существующую
`.venv`; начальная установка описана в README.md. Для desktop нужны Rust,
Visual Studio Build Tools и Windows SDK, для генерации — локальные модели и runtime.

```powershell
npm run backend:dev
npm run frontend:dev
npm run desktop:dev
npm run desktop:build
```

Web-разработка требует отдельно запущенного backend на `127.0.0.1:8000`.
Desktop запускает backend самостоятельно на выбранном свободном loopback-порту.

Проверки выбирай по затронутому поведению:

```powershell
npm --prefix frontend run build
.venv\Scripts\python.exe -m unittest discover -s tests -v
.venv\Scripts\python.exe tests/evaluate_user_queries.py --history
.venv\Scripts\python.exe tests/benchmark_rag.py --phase requests --repeats 2
.venv\Scripts\python.exe tests/benchmark_semantic_graph.py
.venv\Scripts\python.exe tests/benchmark_graph_retrieval.py --answers --repeats 2
.venv\Scripts\python.exe tests/evaluate_universal_review.py --repeats 2
```

`frontend build` проверяет TypeScript и сборку. Новый набор в `tests/` проверяет
пользовательские сценарии, диалоги, HTTP/Live, отмену, файловые границы,
SQLite-журнал индекса, свежесть векторов/графа, доказательства и бюджет контекста.
Offline-тесты используют временные базы и контролируемые ответы провайдера.

Комплект Colab проверяется отдельно:
`.venv\Scripts\python.exe -m unittest discover -s tests -p test_fortuna_training.py -v`.
Проверяются совпадение messages с runtime, схема, ссылки и неизвестные операции,
разделение наборов, целостность архива и отсутствие скрытой обрезки.

`evaluate_user_queries.py` отдельно запускает реальные GGUF-модели на свободных
портах, проверяет известные факты и действия. `--history` читает рабочую историю
и воспроизводит до пяти сохранённых чатов в исходном порядке, а также дополнительные
сценарии в активной папке; все записи идут в отдельную базу. Для сравнения другого
GGUF укажи абсолютный путь в `EVALUATION_MODEL_PATH`: рабочая конфигурация не меняется.
Приватные результаты сохраняются в игнорируемой `.user-evaluation/`, системное
открытие заменено наблюдателем. Не добавляй эти результаты в Git.
Неуспешная оценка возвращает код 1. Нельзя ослаблять проверки ради зелёного отчёта.
Покрытие и известные проблемы описаны в [docs/user-query-evaluation.md](docs/user-query-evaluation.md).
Не сообщай об успешном прохождении отсутствующих или незапущенных проверок.

`evaluate_universal_review.py` проверяет на реальной GGUF нейтральные документы:
участников, объекты, направление отношений, пример, намерение, совет и конфликт
источников, включая верные положительные ответы. Использует ту же изоляцию
хранилищ и серверов; результаты остаются в `.user-evaluation/`.

`benchmark_rag.py` — добровольный реальный замер на синтетических источниках:
фазы `audit`, `overview`, `requests`, `graph` и `all`; `--model` выбирает GGUF
без изменения конфигурации. Стартап, прогрев и индексация отделены от ответов.
Пары batch=1/2 идут в чередующемся порядке с новыми сессиями; сохраняются
полные результаты, число LLM-вызовов, токены и их метрики, медианы и проверки
известных/отсутствующих фактов. Вывод находится в `.user-evaluation/`;
проверяются хеши рабочей базы и сохранённого выбора модели. Только собственные
серверы запускаются и останавливаются. Два повтора не дают надёжного p95.

`benchmark_semantic_graph.py` проверяет смысловые связи на установленной Nomic GGUF
и синтетических документах с собственными SQLite, Chroma и сервером embeddings;
chat-модель не запускается. `tests/test_semantic_graph.py` проверяет дополнение
обычного поиска и границы области, `tests/graph_workbench.browser.cjs` — карту
документов и обычный чат на подменённых API. Подробности в `docs/graph-workbench.md`.

## Правила работы

- Сохраняй существующую историю, документы и совместимость API. Миграции SQLite
  должны учитывать существующие базы и повторный запуск.
- Общая библиотека документов и выбранный workspace — разные источники.
  Сохраняй разделение их индексов и фильтрацию по workspace.
- Сохраняй ограничения файлового доступа: проверку корня workspace, путей,
  символьных ссылок, Windows junction-папок и допустимых форматов.
  Не расширяй возможности навыков неявно. Поддерживаемый Python — 3.12 или новее.
- Не удаляй рабочие базы, Chroma, модели, `.env`, credentials и токены при очистке.
  В dev данные находятся в `api/`, в установленном desktop — в AppData приложения
  `local.kontur.rag`; точные пути определяются настройками.
- Не добавляй секреты, содержимое личных документов, рабочие базы или GGUF в Git
  и документацию. Примеры настроек добавляй в `api/.env.example` без секретов.
- Для вопросов об API, настройках, версиях и особенностях библиотек используй
  текущую документацию через Context7: сначала
  `npx ctx7@latest library <официальное имя> "<конкретный вопрос>"`, затем
  `npx ctx7@latest docs <полученный /org/project> "<конкретный вопрос>"`.
  Если пользователь дал ID, шаг library можно пропустить. Выбирай релевантный
  официальный источник; не более трёх команд на вопрос. Для отдельных тем делай
  отдельные docs-запросы. Не включай секреты в запросы. При quota error сообщи
  пользователю о `npx ctx7@latest login` или `CONTEXT7_API_KEY`; при сетевой ошибке
  повтори вне sandbox, только если действующие разрешения позволяют такой запуск.
  Для обзора проекта, рефакторинга и обычной бизнес-логики Context7 не нужен.
