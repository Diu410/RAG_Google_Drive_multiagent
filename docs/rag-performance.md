# Ускорение RAG и практическая роль графа

## Модельные вызовы

Смысловой аудит проверяет до двух утверждений одним запросом. Каждый элемент
имеет собственные `id`, цитату и контекст; соседние элементы не являются
источниками доказательств. Все поля сравнения и ровно одна оценка каждого ID
обязательны. Детерминированные защиты субъекта, адресата, направления отношения,
лексической подмены и модальности применяются отдельно к каждой оценке.

Пакет отправляется только при достаточном бюджете контекста. При ошибке,
обрыве или неполном результате выполняются отдельные проверки. Отмена
распространяется наружу без повторов. Настройка `EVIDENCE_AUDIT_BATCH_SIZE=1`
отключает пакеты; значение по умолчанию — `2`. Провайдеры без явно заявленной
поддержки пакетного аудита сохраняют прежний контракт. Пакеты используются
в проверке готового ответа и подготовке фактов обзорного ответа workspace.

В профиле FAST короткий обзор сразу возвращает неизменённые проверенные
предложения с атрибуцией источникам: без писателя и проверки нового пересказа.
Область `EXPLANATORY`/`LIMITED` и предупреждения рассчитываются как прежде.
При локальном выборе доказательств по ID BALANCED также возвращает проверенные
содержательные предложения абзацами, без нового пересказа. Для REASONING и
провайдеров с прежним контрактом цитат пересказ проверяется независимо.
Аудит FAST/BALANCED выполняется без рассуждения. Подготовка нативного BALANCED
получает 128 токенов рассуждения для сохранения субъектов и условий; REASONING
использует свой отдельный бюджет. Общие ограничения времени,
обзор персонажа без цепочки исправлений и новые замеры:
[response-latency.md](response-latency.md).

Автоматическая редактура в FAST выполняет draft → edit, вместо пяти генераций
draft → edit → enhance (два варианта) → merge. Пустой retrieval завершает
автоматическую цепочку до редактора. Полная автоматическая цепочка остальных
профилей и отдельные ручные этапы доступны как прежде.

HTTP-клиенты провайдера переиспользуют соединения. Асинхронный клиент создаётся
и закрывается на собственном I/O loop; отмена по-прежнему закрывает поток
конкретной генерации. Только успешные результаты tokenizer кешируются.
При слишком большом prompt размер следующего сокращения учитывает превышение
бюджета; каждый результат по-прежнему проверяется tokenizer. Это уменьшает
число повторных подсчётов на больших блоках источников.

Менеджер llama-server также использует постоянный клиент для readiness/alias.
Эти ответы не кешируются: остановленный сервер или неверная модель должны
сразу стать видны. Остановка закрывает клиент, следующая проверка создаёт новый.

Однозначные информационные вопросы без запрошенных операций и последовательности
шагов пропускают LLM-планировщик workflow. Для активной папки источник выбирается
по правилу без модельного маршрутизатора; явная библиотека и распознанная беседа
сохраняют свои маршруты. Поиск и проверка фактов остаются. Вопросы об имени и конкретных параметрах получают краткий
бюджет по правилам, без отдельного LLM-запроса; просьба подробного анализа
сохраняет приоритет. Краткий генератор отвечает только на запрошенные сведения.
Другие короткие информационные вопросы получают обычный бюджет без LLM-классификации.
Обычная нативная проверка использует ID неизменённых предложений и исходных
цитат с независимым смысловым аудитом. При истечении времени сохраняются
завершённые оценки; подробности — [partial-answer-checks.md](partial-answer-checks.md).

Защита атрибуции учитывает регулярные падежи ролей на «-тель»: «смотрителя»
узнаётся как явное упоминание роли «смотритель». Сопоставление действия,
модальности и цитаты остаётся независимым; имя нельзя подставлять к анонимному
«я/ты» по соседству с описанием роли.

Метрики `preparation_ms` и `request_total_ms` дополняют существующие метрики
генерации. Подготовка включает readiness, бюджетирование и постановку на I/O loop;
полное время включает подготовку и генерацию. Ошибка до запуска генерации
по-прежнему видна на уровне задачи, а не как успешная метрика генерации.

## Workspace

Повторные синхронизации внутри одного assistant-запроса используют снимок
обхода не старше одной секунды. После долгого модельного этапа снимок
обновляется. Ошибочные и неполные обходы не кешируются. Новый запрос и явная
синхронизация вне assistant-запроса всегда выполняют новый обход.

Неизменённые строки файлов не переписываются в SQLite; сохраняется их
`indexed_at`. Удаление определяется только полным успешным обходом. Проверки
корня, форматов, символических ссылок и junction остаются в файловом провайдере.
Полнотекстовый отбор workspace пока всё ещё читает ограниченный набор файлов;
постоянный лексический индекс workspace в эту оптимизацию не входит.

## Граф как дополнение обычного поиска

Граф автоматически помогает обычному чату и draft/edit. Кеш точных имён и
идентификаторов позволяет искать цепочки до двух переходов без нового embedding
и MMR, когда конкретный вопрос полностью покрыт фрагментами и лимит источников
сохраняет путь и альтернативные сведения. Иначе выполняется обычный поиск;
сосед добавляется только при новом совпадении по вопросу. Для workspace он
использует остаток бюджета, не сокращая прямые выдержки. Свежесть и область
проверяются для всех использованных источников. Явные запросы файла/папки
не расширяются. Генерация и проверка используют исходный текст. Подробности:
[graph-workbench.md](graph-workbench.md).

Карта в меню визуализирует близость документов по embeddings одним `/graph/map` с областью источника:
узлы документов, линии смысловой близости, силовое размещение. Отдельный рабочий
процесс вопросов и панелей цитат удалён. Выбор области карты не меняет область
обычного чата. Первое построение читает embeddings; кеш ограничен четырьмя
областями и обновляется при изменении индексов или инвентаря.

GraphRAG возвращает уже найденный граф вместе с ответом и больше не повторяет
поиск после генерации. В данных ответа остаются только связи с фрагментами,
выбранными retrieval. Поле `graph.retrieval.graph_added_source_count` показывает,
сколько дополнительных фрагментов граф внёс в контекст относительно hybrid
retrieval. Автоматический слой отмечает `found_by=semantic_graph` и сохраняет
`graph_source_count` в журнале. Это метрика retrieval,
не подтверждение использования каждого фрагмента в итоговом ответе.

Извлечённые отношения не считаются проверенными фактами и не заменяют текст
источников. Области библиотеки и workspace не смешиваются.
Исследование соседних документов может показывать
больше связей, чем участвовало в первоначальном ответе.

При новом извлечении графа цитата должна дословно присутствовать в исходном
фрагменте. Неизвестный или неверный chunk ID заменяется только при единственном
совпадении цитаты; отношения без такой опоры исключаются. Автоматические
`MENTIONS` обозначают присутствие сущности, а не предметный факт. Инструкция
извлечения отдельно требует сохранять направление действия и не выводить
место, владение или причинность по соседству слов. Наличие цитаты всё равно
не доказывает корректность её трактовки. Для старых графов нужна обычная
переиндексация; рабочие индексы при оптимизации не изменяются.

Старые API окружения, цепочек и выбора цитат сохранены для совместимости;
новая карта их не вызывает. Ни сходство embeddings, ни совпадение цитаты
не позволяют представлять отношение как доказанный факт реального мира.

## Проверка эффективности

Offline-тесты контролируют число вызовов, полноту пакетных оценок,
изоляцию доказательств, отмену, сохранение проверенных фактов, обновление
workspace и однократный поиск графа. Сокращение числа вызовов не является
измерением реальной задержки или гарантией качества модельной оценки.

Для сравнения GGUF нужно фиксировать вопрос, источники, модель, offload и
бюджеты; сравнивать общее время, входные/выходные токены и число fallback.
Использовать отдельную базу и собственные модельные процессы, как описано
в [user-query-evaluation.md](user-query-evaluation.md). Рабочая история,
индексы, конфигурация и серверы пользователя не должны меняться.

Воспроизводимый замер: `tests/benchmark_rag.py --phase audit --repeats 2`
или `--phase requests`, `--phase overview`, `--phase graph`.
Используй `.venv\Scripts\python.exe`; аргумент `--model` принимает путь GGUF.
JSON в `.user-evaluation/` содержит ответы, проверки, вызовы и реальные метрики.
Два повтора пригодны для поиска узких мест, но не для оценки p95.
Реальные запросы и обнаруженные ограничения описаны в
[замерах от 6 октября 2026](rag-benchmark-2026-10-06.md).
