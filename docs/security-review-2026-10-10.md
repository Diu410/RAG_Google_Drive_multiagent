## 2. Граница локального API

Desktop и стандартный dev-запуск слушают loopback, а CORS перечисляет конкретные
origin. Это полезные ограничения. Но маршруты выбора workspace, чтения файлов,
истории, загрузки, удаления документов и генерации не требуют подтверждения
принадлежности клиента приложению.

На изолированном API получены следующие результаты:

- `POST /upload-doc` с multipart и `Origin: https://review.invalid` — HTTP 200;
  обработчик загрузки вызван. Заглушка исключает реальную запись документов.
- `GET /workspaces/{id}/file` с `Host: review.invalid` — HTTP 200 и текст
  синтетического файла. Проверки Host нет.
- JSON POST без Content-Type с чужим Origin — HTTP 422, состояние не изменено.
  Этот вариант обхода не подтвердился.

CORS блокирует чтение multipart-ответа посторонним JavaScript, но обработчик уже
выполнен. Это серверная предпосылка для межсайтовой загрузки документов. Отсутствие
Host-проверки создаёт предпосылку для DNS rebinding. Браузерная эксплуатация
зависит также от ограничений доступа браузера к локальной сети и не проверялась
end-to-end; воспроизведение не доказывает работоспособность атаки в каждом браузере.
Другой локальный процесс может обращаться к API непосредственно.

Рекомендуется случайный токен на запуск, передаваемый desktop-клиенту через
его IPC, проверка токена для чувствительных API, допустимых Host и Origin для
изменяющих запросов. Для web/dev нужен явный механизм выдачи токена. Защита должна
охватывать импорт, голос, граф, историю и совместимые маршруты `/query` и `/agent/*`.

## 3. Открытие исполняемых файлов

`FilesystemProvider.open_file` проверяет корень, ссылки и существование файла,
затем вызывает `os.startfile` без ограничения типа файла. Windows воспринимает
`.cmd`, `.bat`, `.exe` и часть других форматов как запуск, а `.lnk` может указывать
на исполняемую команду. Запрос ассистенту открыть `.cmd` тоже проходит;
в воспроизведении системный opener заменён наблюдателем, реальный процесс не запускался.

Это не произвольное выполнение кода без запроса пользователя: нужен запрос на
открытие файла. Но пользовательская операция открытия документа становится
выполнением содержимого файла. Нужен отдельный список безопасных форматов для
открытия; исполняемые файлы, ярлыки и скрипты следует отклонять в этом навыке.
Форматы, разрешённые для чтения текста, не должны автоматически разрешать запуск.

## 5. Ресурсы и полнота извлечения

Размер HTTP-файла ограничен в `read_limited`, когда FastAPI уже получил UploadFile.
Это не общий предел размера HTTP-тела до form-парсинга. Для Drive этого ограничения
вообще нет: файл скачивается целиком в BytesIO, рекурсивный обход накапливает все
документы и не ограничивает общий объём, глубину или время.

DOCX читает целый `word/document.xml` без проверки распакованного размера.
Синтетический архив 2300 байт извлёк 2 097 152 символа. Проверка входных мегабайт
не предотвращает такое расширение. PDF/OCR не ограничивает число страниц,
размер растеризации или длительность Tesseract. Нужны бюджеты распакованных
данных, страниц, пикселей и времени, плюс ограничение параллельных тяжёлых задач.
Разбор недоверенных документов желательно выполнять в отдельном процессе,
который можно завершить при превышении бюджета.

`load_pdf_complete` намеренно отказывает при пустом OCR пропущенной страницы,
но `chroma_utils.load_pdf` ловит это как любое исключение и возвращает PyMuPDFLoader,
если на других страницах есть текст. В итоге неполный документ индексируется.
Воспроизведение подменяет только отказ полного extractor и резервный loader,
чтобы показать именно эту ветку без установленного OCR. Нужно различать отказ
полноты и потерю формул; первый сохранять как отказ либо явно неполный результат.

Drive пропускает ошибки отдельных файлов, а ответ API считает только уже
извлечённые группы. Пользователь не получает полного списка пропущенных файлов.
`WorkspaceDocumentReader` дополнительно обрезает извлечённый текст до двух
миллионов символов, возвращая обычную строку без флага обрезки. Нужен общий
результат извлечения с охватом, пропусками и причиной отказа.

## 6. Приватность и надёжность

Workspace понимает `.json`, `.ini`, `.conf` и другие форматы, но не исключает
`token.json`, `credentials.json`, service-account JSON по имени. Выбор проекта
как workspace делает такие файлы доступными чтению и индексации. Это особенно
важно при включении внешнего model/embedding endpoint. Требуется политика
исключений для индексации секретов и отдельное явное чтение при необходимости.

INFO-журнал извлечения содержит первые 100 символов страниц, голосовой журнал —
первые 100 символов распознанного текста. Передача backend.log для диагностики
может раскрыть данные. По умолчанию достаточно ID, длительности и размеров;
текстовые превью должны включаться отдельно.

`get_chat_history` читает всю историю текущей эпохи и только после этого Core
берёт последние шесть сообщений. Ограничение prompt не ограничивает этот расход
памяти и чтения базы. В `/agent/*` есть ограничения основных строк, но отсутствуют
суммарные ограничения `context`, `chat_history`, `enhanced`, `comment` и evidence
в ручной проверке. Нужны лимит истории в SQL, ограничение тела запроса и
суммарный бюджет коллекций. Это также касается произвольного chat JSON.

Desktop-миграция использует `copy2` для SQLite и `copytree` для Chroma и создаёт
целевые каталоги сразу. Параллельная запись старого backend или прерванный перенос
могут оставить несогласованные хранилища; наличие файлов препятствует повторному
копированию. Нужны согласованный снимок, staging, проверка и отметка завершения.
Повреждение настоящих пользовательских баз для проверки не моделировалось.

При ошибке poll `/api/model-status` hook сохраняет прежнее `ready=true`.
Отдельное состояние недоступности и тайм-аут poll позволят UI корректно отражать
разрыв связи. Общие API-запросы тоже не имеют тайм-аута по умолчанию.

## 7. Сопровождаемость и границы проверки ответов

`workspace.py` содержит 1971 строку, его `execute` — 610; `_process_input`
в Core — 374; `App.tsx` — 1923. В этих местах соединены маршрутизация,
файловый доступ, генерация, повторная проверка, восстановление и состояние UI.
Выделение extraction, orchestration и восстановления ответа позволит проверять
их контрактами и уменьшит риск взаимного влияния исправлений.

Узкие правила направления «подвластен», самоназвания, адресата и специализации
определений полезны как регрессии. Они не доказывают устойчивость проверки
на новых языковых конструкциях. Следует сохранять причины guard-решений, расширять
контрастные тесты и оценивать проверки на отдельном корпусе, а не добавлять
новое исключение после каждого конкретного ответа модели.

Обычный библиотечный `DOCUMENT_QA` по умолчанию отсутствует в
`VERIFIER_AUTO_STRATEGIES`, а Live-ветка KnowledgeSkill пропускает проверку.
Это сознательная оптимизация; ей нельзя приписывать гарантии проверенных
workspace-обзоров. В UI нужно различать ответ по источнику и ответ с отдельным
аудитом. `confidence` рассчитывается эвристически; калибровка как вероятности
истинности в этом ревью не подтверждена.

В репозитории не найден workflow CI и самостоятельные браузерные тесты.
Offline-набор хорошо покрывает backend-регрессии, но TypeScript и сборка не
проверяют пользовательские взаимодействия. Приоритетное расширение — CI для
существующих проверок и несколько браузерных сценариев чата, отмены, переключения
модели, графа и отказа backend.
