# Ревью «Фортуны» — 21 октября 2026 года

Проверен код относительно `c5e7b5b`, документация, маршруты обычного ответа,
хранение чатов, файловый контекст и индексы. Ниже сохранены исходные находки
ревью и предложения по развитию. Затем внесены исправления пяти находок;
текущее состояние описано в разделе «Исправления после ревью» в конце документа.

## Текущее устройство

React/TypeScript → `/assistant/stream` → `AssistantCore` → маршрутизация и навыки
workspace/knowledge → поиск источников → генерация и внутренняя редактура →
контекстная сверка с независимым аудитом → транзакционное сохранение ответа.
Совместимые `/assistant/input`, `/query`, `/agent/*` и Live сохранены.

Основной режим сверки — contextual: он сохраняет связный текст, включая
неподтверждённые предложения с замечаниями. Strict остаётся отдельным режимом.
Граф помогает выбирать источники, но не доказывает отношения. Библиотека и
workspace имеют отдельные области поиска. Chat GGUF и embeddings обслуживаются
разными локальными серверами, активна одна chat-модель.

Сильные стороны: сохранение ответа, истории модели и завершения задачи одной
SQLite-транзакцией; восстановление индексов по журналу; проверка Host/Origin и
токена локального API; ограничения файловых действий и извлечения; изолированные
регрессионные тесты. Проблемы старого security-review нельзя целиком переносить
на текущий код: существенная часть исправлена 15 октября.

## Находки

### 1. Высокий: вопросы по длинному явно названному файлу теряют сведения в конце

Код: `api/workspace.py:1235–1241`; аналогичные ветви на строках 1243–1247,
1264–1270 и 1305–1309.

После разрешения имени возвращается `content[:limit]` и выполняется ранний
выход. Поиск подходящих фрагментов внутри файла не производится. В отличие от
обычного поиска эта ветвь также не возвращает сведения об охвате.

Воспроизведение: синтетический `LongReport.md`, 24 027 символов; контрольный код
стоит в конце. Вопрос «Какой контрольный код в LongReport.md?» с обычным лимитом
`relevant_context` получает первые 12 000 символов, без кода и без `coverage`.
Это воспроизведение отбора контекста, без LLM: конкретный ложный ответ модели
в этом прогоне не заявляется. У генератора и проверяющего отсутствует нужное
доказательство, поэтому проверка не может компенсировать потерю при поиске.

Улучшение: разрешённое имя должно ограничивать область поиска этим файлом.
Внутри неё следует ранжировать фрагменты по вопросу, сохраняя позиции и соседний
контекст. Для обзора нужен отдельный механизм охвата разделов. Во всех ветвях
передавать объём прочитанного, пропуски и причину ограничения.

Критерий готовности: факты в начале, середине и конце длинного файла доступны
по соответствующему вопросу; недостаточный охват явно отличается от отсутствия
сведений в документе.

### 2. Средний: смена workspace может перенести прежний активный файл

Код: `api/workspace.py:199–221`, вызов в `api/assistant_core.py:520–523`.

`bind_session` меняет `workspace_id`, но сохраняет `workspace_file` и
`workspace_path`, если новые значения не переданы. При следующем запросе эти
поля уже считаются контекстом новой папки.

Воспроизведение через Core: прочитать `ReviewNote.md` в папке A, выбрать папку B,
отправить «Привет». После этого `session_file(session_id, B)` возвращает
`ReviewNote.md`, хотя файл в B не выбирался. Если такое относительное имя есть
в B, последующее «в этом файле» может обратиться к другому документу. Это ошибка
контекста, а не доказанный выход за файловые границы.

Существующий `test_workspace_switch_clears_previous_file_and_directory`
проверяет смену с явным чтением нового файла, которое перезаписывает поле;
переход через обычный диалог им не покрыт.

Улучшение: при изменении `workspace_id` атомарно очищать прежние относительные
путь и файл, затем применять явно переданные новые значения.

### 3. Средний: обновление списка чатов оставляет старую версию в кеше

Код: `frontend/src/useChats.ts:30–35`.

Выражение `full.get(item.id) || item` всегда предпочитает загруженный объект
сервера прежнего запроса, не сравнивая `version`. Новые метаданные из страницы
теряются. Детальная загрузка привязана к изменению `active`: повторное обновление
списка само по себе не обновляет уже выбранный чат.

Воспроизведён фактический код hook с подменой React state и API, без браузера:
в кеше версия 1 / `OLD TITLE`, API возвращает версию 2 / `NEW TITLE`; после
`load()` в состоянии остаётся версия 1 / `OLD TITLE`.

Следствие: интерфейс показывает устаревшее название или историю, а очередное
сохранение получает 409 при корректной работе серверной защиты версий.
Сценарий актуален, например, при изменении из второй вкладки.

Улучшение: переиспользовать полные сообщения только при совпадающей версии.
При новой версии объединить свежие метаданные с состоянием загрузки и получить
актуальную детализацию выбранного чата. Конфликт сохранения должен вести к
доступному действию перезагрузки, сохраняя введённый пользователем текст.

### 4. Средний: сохранённые mtime и размер позволяют читать старый текст файла

Код: `api/workspace.py:360–367`, `api/workspace_document_reader.py:58–63`.

Индекс считает содержимое изменившимся по размеру и `st_mtime_ns`. Кеш
извлечённого текста использует те же признаки. Если заменить текст на текст
той же длины и восстановить mtime, не обновляются ни хеш, ни кеш чтения.
Такое сохранение метаданных возможно при восстановлении файлов и некоторых
сценариях синхронизации.

Воспроизведение: сначала прочитать `Old value: AAA`, записать `New value: BBB`,
восстановить mtime через `os.utime`, выполнить sync. В базе остаётся старый хеш,
он не совпадает с текущими байтами; `read_text_file` возвращает старый текст.
Это требует указанного сочетания метаданных; обычное изменение mtime уже
обрабатывается существующим кодом.

Улучшение: объединить контроль свежести индекса и reader. Использовать
идентичность файла и дополнительные признаки изменений, события файловой
системы, а также повторную проверку содержимого. Перед использованием старых
векторов или выдачей кеша для явно запрошенного файла проверять текущую ревизию.
Один дополнительный timestamp не гарантирует обнаружение любой замены.

### 5. Средний: внутренняя редактура не обеспечивает резерв времени для сверки

Код: `api/answer_editing.py:18–40`, `api/llama_provider.py:318`,
`frontend/src/App.tsx:524`.

Редактура проверяет остаток времени только перед началом этапа. Ограничение
`max(20, request_seconds * .35)` не задаёт дедлайн самого редактирования.
Генерация может занять почти весь оставшийся общий бюджет. Обычный UI включает
редактуру через `use_multi_agent:true`.

Проверка механизма с управляемым остатком: FAST, перед редактурой 85 секунд,
успешный этап расходует 80 секунд. Новая формулировка принимается, для сверки
остаётся 5 секунд. Это детерминированная симуляция расходования бюджета,
не измерение времени реальной GGUF и не доказательство частоты таких отказов.

Улучшение: выделять этапу собственный дедлайн, заканчивающийся до общего
дедлайна на резерв проверки. Резерв оценивать по длине ответа, источникам и
метрикам модели. Если редактура не укладывается, проверять предыдущую завершённую
версию. Один порог перед запуском этого не обеспечивает.

## Предлагаемый порядок работ

1. Исправить выбор фрагментов явно названного файла и изоляцию активного
   файлового контекста. Это напрямую влияет на предмет ответа и доступность фактов.
2. Исправить слияние версий чатов и согласовать проверки свежести reader/индекса.
3. Ввести бюджеты фаз и измерять полный путь отдельно для FAST/BALANCED/REASONING:
   поиск, генерация, редактура, сверка, итоговый статус. Эффект дополнительной
   редактуры оценивать по качеству и задержке на одном наборе вопросов.
4. Постепенно разделить `workspace.py` (2077 строк) на файловый доступ,
   извлечение контекста и выполнение навыка; `App.tsx` (1742 строки) — на чат,
   голос и управление workspace. Сначала закрепить контракты, затем переносить
   части без изменения поведения. Добавить TypeScript-типы вместо `any` в транспорте.
5. Развивать независимый набор нейтральных сценариев качества: длинные файлы,
   смена источников, отрицания, отношения, отсутствие факта, противоречия,
   положительные корректные ответы. Отчёт должен разделять ошибки retrieval,
   генерации и сверки; единый процент успешных unit-тестов этого не показывает.
6. Включить существующие браузерные сценарии в CI и отдельно проверять собранный
   installer. Сейчас `.github/workflows/checks.yml` запускает backend-тесты,
   проверку секретов и frontend build, но не браузерные сценарии и desktop smoke.

Дальнейшее масштабирование: вынести сообщения из растущего JSON чата в отдельную
таблицу, чтобы не переписывать всю историю при каждом ответе. Для больших папок
заменить полный обход и чтение до 500 файлов на запрос инкрементального текстового
индекса с обязательной проверкой свежести. Нативное извлечение PDF/DOCX изолировать
в рабочем процессе с принудительным пределом времени и памяти; текущие лимиты
кооперативные, что уже отражено в документации исправлений от 15 октября.

  успешно, 74.557 секунды. Данные изолированы тестовым окружением.
- TypeScript: этап `tsc --noEmit` в штатной build-команде прошёл.
- Штатная `npm --prefix frontend run build` остановилась при загрузке Vite config:
  esbuild получил отказ доступа к родительскому каталогу в данной среде.
- Production-сборка через Vite JavaScript API с `configFile:false` и тем же
  React plugin успешно завершилась: 1946 модулей, 4.41 секунды. Исходный конфиг
  не менялся. Это отдельный обход ограничения среды, а не успешный штатный build.
- `scripts/check_secrets.py`: совпадений в отслеживаемых исходниках нет.
  Это не полный аудит секретов и не подтверждение отзыва исторического ключа.
- Четыре описанных воспроизведения и симуляция бюджета выполнены отдельно от
  существующего набора тестов; скрипты в игнорируемой
  `.user-evaluation/review-2026-10-21/`. Они используют синтетические данные.

Реальные GGUF-ответы, OAuth Google Drive, голос, браузерные сценарии, Rust и
installer в этом ревью не запускались. Новая оценка уязвимостей зависимостей
не проводилась. Рабочие модели, история, документы и настройки не изменялись.

## Исправления после ревью

Все пять находок получили исправления в рабочем дереве:

| Находка | Реализованное поведение |
| --- | --- |
| Длинный выбранный файл | `workspace_context.py` выбирает дословные окна по вопросу внутри файла; обзор и неизвестная лексика получают распределённую выборку с концом текста. Позиции и неполный охват сохраняются; ответ показывает ограничение. Полные строки с инструкциями исключаются до выдачи обрезанных выдержек. |
| Смена workspace | Один SQL UPDATE сбрасывает прежние файл и каталог при смене области и применяет явно переданные значения. В прежней папке контекст сохраняется. |
| Кеш чатов | Сводки с новой версией заменяют старый кеш, активная история загружается повторно. Устаревший ответ списка не заменяет более новую локальную версию. Обновлена также пагинация. |
| Сохранённые размер и mtime | Общая ревизия индекса и reader включает идентичность файла и время изменения метаданных; Windows получает ChangeTime, недоступное значение заменяется хешем байтов. Есть проверка изменения во время извлечения и повторяемая аддитивная миграция SQLite. |
| Бюджет редактуры | Дочерний дедлайн оставляет сверке `max(20, request_seconds * .35)` секунд; таймаут сохраняет предыдущий текст, родительский scope и отмена пользователя сохраняются. Резерв пока задан профилем, без адаптации по реальным замерам. |
