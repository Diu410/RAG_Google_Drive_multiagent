# Обслуживание поискового индекса рабочей папки

Рабочая папка открывается слева, без дополнительной плашки над чатом.
Параметры источников остаются внутри Workspace. Под ответом только один блок
«Источники ответа»: структурированные фрагменты для новых записей либо прежний
текст контекста для старых. Данные истории не удаляются и не переписываются ради
устранения визуального дублирования.

## Что доступно

В окне Workspace сохраняется кнопка «Индексировать папку». Это инкрементальное
обновление, не полная повторная обработка: неизменённые документы не проходят
embeddings заново. Оно относится ко всей рабочей папке с вложенными папками,
независимо от выбранных для ответа файлов.

Рядом со счётчиком актуального индекса теперь различаются:

- новые документы без индекса (`PENDING`);
- изменённые документы, для которых осталась старая версия индекса (`STALE`);
- документы с ошибкой последней обработки (`FAILED`);
- читаемые по метаданным документы, для которых обход не смог получить стабильный
  хеш (`UNAVAILABLE`).

Состояния взаимоисключающие; их сумма вместе с `INDEXED` равна числу доступных
документов в текущем снимке метаданных. Неподдерживаемые/исключённые форматы и
секретные файлы не становятся доступными из-за нового интерфейса.

«Проверить изменения» заново обходит папку и обновляет состояние без вызовов
embeddings или chat-модели. Это не непрерывное наблюдение за диском: интерфейс
показывает время проверки. Список требующих внимания документов ограничен первыми
50 с явным сообщением об ограничении; общие счётчики учитывают остальные.

«Повторить ошибки» доступно при неудачной индексации. Режим повторяет только
документы со статусом ошибки; новые и изменённые без ошибки остаются для обычного
обновления. Очистка отсутствующих файлов в этом режиме не выполняется.
Ошибки последнего запуска различают извлечение/чтение, построение/сохранение
embeddings и изменение источника во время обработки. В ответ API попадают пути
внутри workspace и коды, не исходные тексты исключений с возможными абсолютными
путями или параметрами транспорта. В SQLite остаётся прежняя диагностика ошибки.

Без актуальных embeddings остаётся лексический поиск; это не
равноценная замена смысловому поиску и не доказательство полного охвата папки.
Постоянный текстовый слой, его отдельный счётчик и ограниченный холодный fallback
описаны в [workspace-text-index.md](workspace-text-index.md).

## Актуальность и сохранение индекса

Перед извлечением, после него и перед SQLite-решением о публикации новой порции
векторов сверяется ревизия реального файла. SQLite дополнительно проверяет
исходные `content_hash` и `revision`. Изменение во время embeddings отклоняет
публикацию: staging-векторы удаляются через существующий журнал транзакций,
предыдущие векторы сохраняются. Старая версия не считается актуальным источником.
Повтор берёт новое содержимое, а не старый извлечённый текст.

При неполном обходе (лимит или ошибки файловой системы) очистка отсутствующих
векторных/графовых записей откладывается. Отсутствие наблюдения не является
доказательством удаления. При следующем полном обычном обновлении очистка
возобновляется. Удаляются только записи индекса, не файлы пользователя.

Как и прежде, новое внешнее изменение сразу после успешной проверки нельзя
исключить файловым наблюдением: свежесть повторно проверяется при поиске и чтении.
Это не блокировка файлов от внешних редакторов и не новая фоновая очередь.

## Совместимость API

`GET /workspaces/{id}/index-status` сохраняет прежние поля и добавляет
`pending_documents`, `changed_documents`, `unavailable_documents`, `issues`,
`issues_truncated` и время `checked_at`. Сначала выполняется обход метаданных.

`POST /workspaces/{id}/vector-sync?extract_relations=false&mode=update` сохраняет
прежний обычный режим. Новый `mode=retry_failed` выбирает только ошибки. Неизвестный
режим — 422. Отсутствие параметра сохраняет старое поведение. API с
`extract_relations=true` остаётся совместимым; повтор учитывает и неудачные графы.
Обычный UI по-прежнему не запускает LLM-извлечение графовых отношений.

В результат добавлены `skipped`, признаки неполного обхода `scan_truncated` /
`scan_errors`, `cleanup_deferred` и до 50 элементов `issues` с `path` / `code`.
Успех отдельных файлов не означает успех всех документов: сохраняются счётчики
отказов. Маршруты требуют обычный токен локального API.

## Проверка

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -p test_workspace_index_maintenance.py -v
.venv\Scripts\python.exe -m unittest discover -s tests -p test_index_and_plans.py -v
npm --prefix frontend run build
node tests/workspace_sources.browser.cjs
node tests/local_tools.browser.cjs
```

Offline-набор проверяет состояния, ограничение диагностики, инкрементальное
обновление, выборочный повтор, отказ чтения/embeddings, откат при изменении в
процессе embeddings с восстановленным mtime, отложенную очистку и HTTP-доступ.
Браузерный сценарий использует production UI, отдельные настоящие API/SQLite/файлы,
контролируемые автора и embeddings с однократным отказом; также проверяет один
блок источников для workspace/библиотеки/старой истории. Это не проверка качества
или скорости реальной GGUF. Windows installer и непрерывная фоновая индексация
в этот этап не входят.

Результат проверки реализации: полный offline-набор — 746 тестов успешно,
профильный новый набор — 12 тестов успешно; production build с TypeScript,
`git diff --check` и оба указанных browser-сценария прошли. Личные документы,
рабочие базы и выбранная модель для этих прогонов не использовались.
